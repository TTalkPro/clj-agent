# G-02 同一轮多条审批

> 设计依据：[designs/agui-borrow.md](../designs/agui-borrow.md) §2。依赖：**runtime agent 先做 client 侧**（多 pending + 逐条决策 + PauseStore 快照）；G-01。
> 状态：✅（2026-11-08；client 侧由 runtime agent 完成后在主目录实现）

## 范围

**client（runtime agent，`react.clj` / `simple_agent.clj` / `pause.clj`）——本项的前置，不归 agui：**
- 暂停结果多给 `:pending-tools [...]`（保留 `:pending-tool` = 第一条）；`:loop-state` 多给 `:pending-ids [...]`（保留 `:pending-id`）；PauseStore 快照兼容旧形状（只有 `:pending-id` ⇒ 单条）。
- resume 接受逐条决策：`{:decisions {"tc1" {:decision :approved :args {...}} "tc2" {:decision :rejected :message "..."}}}`。
- 缺席的 id 按当前 gate 仍需审批 ⇒ 抛 `ex-info`（`:type` 由 runtime agent 定，建议 `:interrupt-incomplete`，带 `:pending` 列表）；未知 id ⇒ `:interrupt-unknown`。

**agui（本模块，client 就绪后）：**
- `terminal-payload` 带 `:pending-tools`；`codec/interrupt-of` → `interrupts-of`，`outcome.interrupts` 一次发全。
- `runtime/awaiting` / `/pending` 列多条。
- 路由：`resume[]` 全量校验——对不上 ⇒ 409 `interrupt_unknown`；解析失败 ⇒ 400 `interrupt_bad_resume`；client 抛 incomplete ⇒ 409 `interrupt_incomplete`（带仍待答复的 id）。都在起 run 之前判。

## 验收

- client：两条 sensitive 调用 ⇒ `:pending-tools` 两条；逐条决策 ⇒ 一条执行一条拒绝；漏答 ⇒ incomplete。
- agui：`outcome.interrupts` 两条；路由三种 4xx；端到端「一批两条审批，只批一条」⇒ 只执行被批的那条（今天两条都执行——越权）。

- 偏离：错误在路由层以 4xx JSON 回（码小写蛇形，同既有 `interrupt_mismatch`），不是 Keelson 的起 run 后 `RUN_ERROR`；`RUN_ERROR INTERRUPT_*` 只作为绕过路由直接调 `resume-run!` 时的兜底。⚠️ 发现：client 在 resume 抛 incomplete 时会**清掉暂停态**（`finalize` 的 `:error` 分支 `pause-clear*`），所以直接调 `resume-run!` 漏答会丢掉整个审批——这正是路由必须先判的理由；是否让 client 在校验错时保留暂停，需 runtime agent 决定。

### 补记（协调者，2026-11-08）

client 侧原先在 resume 时才抛 `:interrupt-incomplete` / `:interrupt-unknown`，经 `finalize` 的
`:error` 分支会把暂停快照清掉——绕过路由直接调 `resume-run!` / `simple-agent/resume` 漏答一次，
整批审批就丢了。改为：`react/check-decisions!`（公开）在 `simple-agent` 的 `resume-prep` 里、
动任何状态之前先校验，答错直接抛、暂停原样保留；`resume-approval-batch` 复用同一函数。
