> **本文是项目级设计原则的唯一出处（canonical）。**
> 各设计文档**回指本文**，不重述——原则散在个案里的下场，就是下一份文档
> 再把它重新推导一遍（这正是 §1 被提取出来的原因）。

## 1. 无真实需求不建（硬约束，不可违反）

> **抽象要由真实需求触发，不由对齐别人、对称性、或「以后可能要」触发。
> 用户在自己代码里几行就能等价做到的事，框架不长字段、不开 seam、不加协议。**

**出处**：本是 `advisor-alignment-design.md` §1.3 的「立项判据」（「出现真实需求时
再抽」），因在 `tool-calling-manager-design.md` 里被反复重新发现（毙 `deftool
:backend`、毙 PR2/PR3、拆掉一个防御性保护）而提为硬约束。

### 1.1 理由

1. **框架的每个字段都是永久 API 面**。`deftool` 多一个 `:backend`，就永远多一个
   要兼容、要文档、要测试、要在每次重构里绕开的东西；用户函数体里的 5 行 HTTP 包装
   删了就没了。**成本不对称：建的代价是永久的，不建的代价是几行。**
2. **假想需求会把形状带歪**。为想象中的场景设计，得不到真实反馈，只能靠对称性和
   对标猜——猜出来的形状在真需求到来时往往不合用（`:backend :http` 只能表达一种
   POST 形状，真实 HTTP 工具要自定义 header / 非 JSON body 时立刻退回手写）。
3. **宿主语言已经免费给的，不要重新实现一遍**。Clojure 里函数是一等值，
   Spring `ToolCallback` 用接口承担的 transport 多态，在这里由**函数体本身**承担。

### 1.2 四问判据

怎么分辨真实需求与假想需求——**每个人都觉得自己的需求是真的**，所以要逐条过：

| 问题 | 真实需求 | 假想需求 |
|---|---|---|
| 现在有人要用吗？ | 有具体场景、具体调用方 | 「以后可能」「为了完整」 |
| 不建的话用户怎么办？ | **做不到**，或代价高到不可接受 | 自己写几行就等价 |
| 换来的是什么？ | **能力**（不建就没有的事） | 只是「更声明式 / 更对称 / 更像 Spring」 |
| 触发条件写得出来吗？ | 写得出具体场景 | 写不出，只能说「万一」 |

### 1.3 落地约束

| 情形 | 约束 |
|---|---|
| 提新抽象 | 先回答 §1.2 四问。四问里有一问落在「假想」列，**不立项**；把理由写进否决记录，供以后重启时对照 |
| 已建的抽象，论据倒了一条 | **重新称剩下的论据有多重**，不假定它跟着变轻，也不假定它还够重 |
| 框架的「防御性机器」 | **同样适用**——为防一个没人会踩的坑而加的保护，也是无真实需求的建造 |
| 已否决的方案 | 保留否决记录，但**重启时须重新设计**，不得直接捡回旧方案 |
| 能立不变量的，不建机器 | 与其造机器去容忍某个用法被违反，不如把不变量写清楚（该不变量已提为 [§3](#3-一个-kernel-绑定一个-tcm不跨边界硬约束不可违反)） |

### 1.4 案例法

判例都出自 `tool-calling-manager-design.md`，**含一次自打脸**：

| 案例 | 判定 | 依据 |
|---|---|---|
| `deftool :backend`（§5） | ❌ 否决 | 用户函数体里写 `(http/post ...)` 5-10 行等价；换来的只是「更声明式」，且表达力反而更弱 |
| PR2 / PR3（§8） | ❌ 否决 | 同上。从「⏸️ 搁置待需求」**改判否决**——有 HTTP/MCP 需求也不做，因为那个需求手写就解决了，**不构成触发条件** |
| `*active-pools*` 自锁保护（§4.3.1） | ❌ 拆除 | 用「子 agent 共用有界池会死锁」论证它，但子 agent **根本不共享引擎**（无继承路径）。主场景是编的；剩下的同线程情形没人碰得到 |
| **`ToolCallingManager` 自己**（§2） | ⚠️ **险些踩中** | 立项两条腿：多 transport（**假想**，已否决）+ 隔离与线程模型可换（**真实**：`react.clj` 的 VT executor 是进程全局 `def`，无舱壁 / 无限流 / 无可关停边界）。**假想那条腿当时看起来比真实那条更有说服力**——这正是本原则要防的 |

> **最要紧的一条**：本原则**对自己也适用**。上表第三行就是作者一边用它毙掉
> `:backend`、一边转头为假想需求建了一套动态变量机器。**标准不能只对别人用。**

## 2. 框架无关（硬约束，不可违反）

> **agent 框架是一个库，不是 web 应用。core 永远不依赖、不捆绑任何 web 框架
> （Luminus / Ring / Undertow / Jetty / Aleph / http-kit-server 一律不行）。**

**出处**：`streaming-async-design.md` §0.5。

### 2.1 理由

1. **依赖方向**：web 应用**依赖**本库，不能反过来。core 一旦依赖某 web 框架，
   等于强迫所有使用者都用它——而 agent 的场景远不止 web（CLI、桌面、批处理、
   MQ 消费者、非 Luminus 的 web 栈…）。
2. **回调原语就是解耦边界**：`on-token / on-complete / on-error + cancel` 是最小的
   push 契约，任何 sink 都能接（http-kit `send!` / Undertow
   `ServerSentEventConnection.send` / Aleph manifold stream / Jetty async body /
   终端 print / core.async channel…）。**框架特定的东西全在适配那一层，core 一无所知。**
3. **越薄的边界越长寿**：web 框架会换（Luminus 默认 server 就在
   http-kit→Immutant→Undertow 间换过几轮），JDK `java.net.http` + 一个回调契约不会。
   绑死某框架 = 跟着它的生命周期走。

### 2.2 落地约束

| 层 | 约束 |
|---|---|
| **库本体**（clj-agent-core / clj-agent-client / clj-agent-provider 的 src） | 零 web 框架依赖。只暴露回调原语（`chat-stream` + on-token/cancel）。传输用 JDK `java.net.http`（非 web 框架） |
| **集成代码** | 只放 `examples/`（文档级、可跑）；**不进 src、不进核心 `:deps`**。web 依赖只在该 example 的 alias 里 |
| **不挑框架站队** | 不做「我们集成 Luminus」这种定位。要给示例就**覆盖多个**（http-kit / Undertow-SSE / Aleph）或讲**通用模式**（「拿到 token 往你的 sink 写」） |
| **若真要发适配器** | 单独的可选模块 + web 依赖标 `provided`/optional，绝不污染 core |

### 2.3 现状

**已满足**：`chat-stream` 只认回调原语、`stream_client` 用 JDK `java.net.http`、
`deps.edn` 无任何 Ring/Luminus/Undertow/web-server 依赖。
**本原则是「守住现状」，不是「待改造」。**

## 3. 一个 Kernel 绑定一个 TCM，不跨边界（硬约束，不可违反）

> **一个 Kernel 恰好绑定一个 ToolCallingManager，且这个绑定<u>就是</u>执行边界。
> 边界<u>内</u>必须一致——工具看到的东西不得因批次大小 / 引擎选型 / filter 挂载而变；
> 边界<u>外</u>不得流通——父 Kernel 的引擎与环境状态不自动流入子 Agent。**

**出处**：`tool-calling-manager-design.md` §4.3.1（拆除 `*active-pools*` 自锁保护时
立的不变量）。原先只是 §1.3 表格里的一个**括号举例**，2026-07-16 用户拍板提为
项目级硬约束——理由见 §3.4：它被埋在别的原则里，导致真要用时没人想得起来。

### 3.1 理由

1. **TCM 是执行引擎**（线程模型 + 隔离边界 + 调度策略）。「引擎」和「边界」是同一个
   东西的两面：`ThreadPoolToolCallingManager` 的舱壁之所以是舱壁，正因为**没有别人
   能挤进这个池**。让引擎跨边界流动，等于宣布舱壁不隔离。
2. **边界内一致，是 TCM 可替换的前提**。`react.clj` 明写「引擎只决定『**怎么**把这批
   跑完』，不决定『**跑的是什么**』」。若换个引擎、或 LLM 多发一个 tool-call，工具
   看到的东西就变了，这句话即是空话——用户无法在不改变语义的前提下选型。
3. **边界外不流通，是子 Agent 之所以是子 Agent**。子 Agent 拿到全新 Kernel + 全新
   TCM，本就是「独立执行单元」的定义。任何**隐式**穿过去的东西（引擎、动态绑定、
   ambient 上下文）都在偷偷把两个执行单元焊在一起——要传就**显式**经 `subagent-config`。
4. **它替掉了一整套机器**。§1.3「能立不变量的不建机器」的原始案例：与其造
   `*active-pools*` 去检测「子 agent 共用池会不会死锁」，不如立下不变量说它们本就
   不共用。**不变量是零成本的，机器是永久成本的。**

### 3.2 两个方向的判据（同一条原则，方向相反）

管的是**执行环境**（ambient state：动态绑定、线程身份、调度可观察到的一切），
**不是**行为本身。先把这条划清楚，否则本原则会把整个 filter 体系判成违反
（见 3.2.1）。

| 方向 | 判据 | 违反长什么样 |
|---|---|---|
| **边界内一致** | 同一 Kernel/TCM + 同一组 filter 下，工具的**执行环境**不得因**调度差异**（批次大小、引擎选型、内联 vs executor）而变 | 同一个工具，LLM 发 1 个 tool-call 时读到 `:acme`、发 2 个时读到 `:none` |
| **边界外不流通** | 父 Kernel 的 TCM / 动态绑定 / ambient 状态不得**自动**流入子 Agent | 父进程的 `binding` 悄悄在子 Agent 的工具里生效；父 TCM 的池被子 Agent 占用 |

**要点**：这两条**不是**互相冲突的，它们是同一条线的两侧。判断任何「某状态该不该
到达某处」时，先问：**中间隔着 Kernel/TCM 边界吗？**没隔着 → 必须一致；隔着 →
必须显式，否则不给。

#### 3.2.1 「一致」管环境，不管行为——filter 改变行为是它的本职

**filter 不在「边界内一致」的禁令里**。挂 `approval-filter` 决定工具跑不跑、挂
`timeout-filter` 决定超不超时——**改变行为正是 filter 存在的理由**，也是用户
显式声明的意图。把「filter 挂载」写进禁令等于禁掉整个 filter 体系。

真正要禁的是**副作用式的环境扰动**：filter 改变了它**没声明**要改的东西。判据：

| | 例 | 判定 |
|---|---|---|
| filter 改**它声明要改**的 | `timeout-filter` 让未声明的工具有了缺省超时；`approval-filter` 拒绝执行 | ✅ 本职 |
| filter 顺手改了**执行环境** | `timeout-filter` 曾把工具搬去 send-off 平台线程，顺带弄丢 `binding` | ❌ 违反 |

**判据一句话**：挂上一个 filter，工具**该**看到它声明的效果，**不该**发现自己的
`binding` 没了、线程模型变了。

> **这条修订的由来**（2026-07-16 code review 自查）：3.2 初稿把「filter 挂载」
> 与批次大小、引擎选型并列写进禁令，字面上会把 `timeout-filter` 与
> `approval-filter` 双双判为违反——而本原则**同期**的落地工作恰恰依赖
> 「挂了 timeout-filter 才有缺省超时」。**原则要能判定违反才算硬约束**：会把合法
> 设计判成违反的表述，援引者只能靠猜哪条算数，等于没有判据。

### 3.3 落地约束

| 情形 | 约束 |
|---|---|
| Kernel ↔ TCM | **1:1**。TCM 是 `Kernel` record 的字段，经 `build-kernel :tool-manager` 注入；一个 Kernel 一个引擎 |
| 子 Agent | `do-run` 用 `subagent-config` 造**全新** Kernel。父 TCM **无自动渠道**流入。用户要共享须在 `:subagent-fn` 里**亲手塞回去**——那是踩坑，不是漏洞 |
| 批内调度 | 内联 / executor / 各引擎的**可观察语义必须逐字段相同**（结果、`:serial` 退化、`:writes` 折叠、动态绑定…）。差异只许存在于「怎么跑」 |
| filter | **不在「一致」的禁令里**——改变行为是它的本职（§3.2.1）。但它只许改**它声明要改**的；顺手扰动执行环境（线程模型、`binding`…）即违反 |
| ambient 状态跨 delegate | **不传导**。`spawn-worker!` 不用 `bound-fn*` 是**故意的**，有测试钉住——它看起来像疏漏，别顺手「修好」 |
| 想让某状态穿到子 Agent | 走 `subagent-config` / prompt **显式**传。没有隐式通道 |
| 发现违反 | 改代码立回不变量，**不建机器去容忍它**（§1.3） |

### 3.4 案例法

| 案例 | 判定 | 依据 |
|---|---|---|
| `*active-pools*` 自锁保护 | ❌ 拆除 | 造机器去防「子 agent 共用池死锁」，而子 agent **根本不共享引擎**。立不变量即可，机器是多余的（本原则的出处） |
| `run-on-executor` 不传导动态绑定（2026-07-16） | 🐛 **必须修** | **违反「边界内一致」**：同一工具因 LLM 临场决定发几个 tool-call 而看到不同 `binding`（1 个走内联 → 可见；≥2 个走 executor → 丢失），换引擎也变。已用 `bound-fn*` 修复 + 测试钉住两个维度 |
| `timeout-filter` 改虚拟线程时丢传导（2026-07-16） | 🐛 **必须修** | **副作用式的环境扰动**（§3.2.1）：它声明要改的是「超不超时」，却顺手把 `binding` 弄丢了。已修 |
| `timeout-filter` 挂上才有缺省超时 | ✅ **不是违反** | filter 改变**它声明要改**的行为，正是本职（§3.2.1）。3.2 初稿的表述会把它误判——已修订 |
| `spawn-worker!` 不传导动态绑定 | ✅ **正确，不改** | **遵守「边界外不流通」**：子 Agent 是新 Kernel + 新 TCM = 新边界，ambient 状态本就不该穿过去 |
| `deftool :timeout` 曾只有挂 filter 才生效（2026-07-16 review#4） | 🐛 **已修** | 与 §3 无关，是 §1 的事：`:serial`/`:retry`/`:return-direct` 都由 kernel/react 直接消费，独 `:timeout` 要用户手动挂 filter——「声明了却静默无效」正是我们要修的那个 bug 换了个位置。现由 `kernel/invoke-tool` 强制（单次调用的时间上限是它的职责），filter 退为「只给未声明的工具兜缺省」 |

> **一次「用错工具」的复盘**（2026-07-16，本原则被提级的直接原因）：
> 上一行那个问题，作者最初是拿 **§1 四问**去答的——结论是「无具体调用方 → 假想
> 需求 → 待定」。**结论碰巧不错，但依据是错的**：不传导不是「还没有人要」，而是
> **原则上就不该**。真需求来了，§1 的答案会翻转（有人要就建），§3 的不会（有人要
> 也不给隐式通道，只给显式的 `subagent-config`）。
>
> **为什么会拿错工具**：本原则当时**只是 §1.3 表格里的一个括号举例**——被埋在另一
> 条原则的插图里，真要用时想不起来。这正是本文开篇那句话的又一个实例：**原则散在
> 个案里的下场，就是下一份文档再把它重新推导一遍**（§1 自己就是这么被提出来的）。
> 提级即是对症。

## 三条原则的关系

它们从三个方向管同一件事——**框架该长什么、不该长什么**：

- §1 管**纵向**：这个抽象该不该存在（需求真不真）。
- §2 管**横向**：这个依赖该不该跨进来（外部边界破没破）。
- §3 管**内部的横向**：这个状态该不该流到那里（内部边界破没破）。

§2 与 §3 都是边界，分工是**边界在哪**：§2 划在**库与外部世界**之间（web 框架不许
进来）；§3 划在**库内部的执行单元**之间（Kernel/TCM 之间不许隐式流通）。

一个提案可能同时受多条约束：

- 「给 core 加个 SSE 适配器」——§2 直接否（core 不碰 web 框架），§1 也会问「用户
  自己往 sink 写 token 要几行？」。
- 「让子 Agent 继承父 Agent 的线程池」——§3 直接否（跨边界），§1 还会问「用户在
  `:subagent-fn` 里自己传要几行？」。
- 「造个机器检测跨边界共享」——§3 说不变量已经立了，§1.3 说**能立不变量的不建机器**。
