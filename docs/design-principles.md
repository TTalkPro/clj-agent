## 1. 无真实需求不建（硬约束，不可违反）

> **抽象要由真实需求触发，不由对齐别人、对称性、或「以后可能要」触发。
> 用户在自己代码里几行就能等价做到的事，框架不长字段、不开 seam、不加协议。**

**出处**：本是 `advisor-alignment-design.md` §1.3 的「立项判据」（「出现真实需求时
再抽」），因在 `tool-calling-manager-design.md` 里被反复重新发现（毙 `deftool
:backend`、毙 PR2/PR3、拆掉一个防御性保护）而提为硬约束。

### 1.1 理由

1. **框架的每个字段都是永久 API 面**。`deftool` 多一个 `:backend`，就永远多一个
   要兼容、要文档、要测试、要在每次重构里绕开的东西；用户函数体里的 5 行 HTTP 包装
   删了就没了。**成本不对称：建的代价是永久的，不建的代价是几行。**
2. **假想需求会把形状带歪**。为想象中的场景设计，得不到真实反馈，只能靠对称性和
   对标猜——猜出来的形状在真需求到来时往往不合用（`:backend :http` 只能表达一种
   POST 形状，真实 HTTP 工具要自定义 header / 非 JSON body 时立刻退回手写）。
3. **宿主语言已经免费给的，不要重新实现一遍**。Clojure 里函数是一等值，
   Spring `ToolCallback` 用接口承担的 transport 多态，在这里由**函数体本身**承担。

### 1.2 四问判据

怎么分辨真实需求与假想需求——**每个人都觉得自己的需求是真的**，所以要逐条过：

| 问题 | 真实需求 | 假想需求 |
|---|---|---|
| 现在有人要用吗？ | 有具体场景、具体调用方 | 「以后可能」「为了完整」 |
| 不建的话用户怎么办？ | **做不到**，或代价高到不可接受 | 自己写几行就等价 |
| 换来的是什么？ | **能力**（不建就没有的事） | 只是「更声明式 / 更对称 / 更像 Spring」 |
| 触发条件写得出来吗？ | 写得出具体场景 | 写不出，只能说「万一」 |

### 1.3 落地约束

| 情形 | 约束 |
|---|---|
| 提新抽象 | 先回答 §1.2 四问。四问里有一问落在「假想」列，**不立项**；把理由写进否决记录，供以后重启时对照 |
| 已建的抽象，论据倒了一条 | **重新称剩下的论据有多重**，不假定它跟着变轻，也不假定它还够重 |
| 框架的「防御性机器」 | **同样适用**——为防一个没人会踩的坑而加的保护，也是无真实需求的建造 |
| 已否决的方案 | 保留否决记录，但**重启时须重新设计**，不得直接捡回旧方案 |
| 能立不变量的，不建机器 | 与其造机器去容忍某个用法被违反，不如把不变量写清楚（如「一个引擎属于一个 kernel，不跨 delegate 边界」） |

### 1.4 案例法

判例都出自 `tool-calling-manager-design.md`，**含一次自打脸**：

| 案例 | 判定 | 依据 |
|---|---|---|
| `deftool :backend`（§5） | ❌ 否决 | 用户函数体里写 `(http/post ...)` 5-10 行等价；换来的只是「更声明式」，且表达力反而更弱 |
| PR2 / PR3（§8） | ❌ 否决 | 同上。从「⏸️ 搁置待需求」**改判否决**——有 HTTP/MCP 需求也不做，因为那个需求手写就解决了，**不构成触发条件** |
| `*active-pools*` 自锁保护（§4.3.1） | ❌ 拆除 | 用「子 agent 共用有界池会死锁」论证它，但子 agent **根本不共享引擎**（无继承路径）。主场景是编的；剩下的同线程情形没人碰得到 |
| **`ToolCallingManager` 自己**（§2） | ⚠️ **险些踩中** | 立项两条腿：多 transport（**假想**，已否决）+ 隔离与线程模型可换（**真实**：`react.clj` 的 VT executor 是进程全局 `def`，无舱壁 / 无限流 / 无可关停边界）。**假想那条腿当时看起来比真实那条更有说服力**——这正是本原则要防的 |

> **最要紧的一条**：本原则**对自己也适用**。上表第三行就是作者一边用它毙掉
> `:backend`、一边转头为假想需求建了一套动态变量机器。**标准不能只对别人用。**

## 2. 框架无关（硬约束，不可违反）

> **agent 框架是一个库，不是 web 应用。core 永远不依赖、不捆绑任何 web 框架
> （Luminus / Ring / Undertow / Jetty / Aleph / http-kit-server 一律不行）。**

**出处**：`streaming-async-design.md` §0.5。

### 2.1 理由

1. **依赖方向**：web 应用**依赖**本库，不能反过来。core 一旦依赖某 web 框架，
   等于强迫所有使用者都用它——而 agent 的场景远不止 web（CLI、桌面、批处理、
   MQ 消费者、非 Luminus 的 web 栈…）。
2. **回调原语就是解耦边界**：`on-token / on-complete / on-error + cancel` 是最小的
   push 契约，任何 sink 都能接（http-kit `send!` / Undertow
   `ServerSentEventConnection.send` / Aleph manifold stream / Jetty async body /
   终端 print / core.async channel…）。**框架特定的东西全在适配那一层，core 一无所知。**
3. **越薄的边界越长寿**：web 框架会换（Luminus 默认 server 就在
   http-kit→Immutant→Undertow 间换过几轮），JDK `java.net.http` + 一个回调契约不会。
   绑死某框架 = 跟着它的生命周期走。

### 2.2 落地约束

| 层 | 约束 |
|---|---|
| **库本体**（clj-agent-core / clj-agent-client / clj-agent-provider 的 src） | 零 web 框架依赖。只暴露回调原语（`chat-stream` + on-token/cancel）。传输用 JDK `java.net.http`（非 web 框架） |
| **集成代码** | 只放 `examples/`（文档级、可跑）；**不进 src、不进核心 `:deps`**。web 依赖只在该 example 的 alias 里 |
| **不挑框架站队** | 不做「我们集成 Luminus」这种定位。要给示例就**覆盖多个**（http-kit / Undertow-SSE / Aleph）或讲**通用模式**（「拿到 token 往你的 sink 写」） |
| **若真要发适配器** | 单独的可选模块 + web 依赖标 `provided`/optional，绝不污染 core |

### 2.3 现状

**已满足**：`chat-stream` 只认回调原语、`stream_client` 用 JDK `java.net.http`、
`deps.edn` 无任何 Ring/Luminus/Undertow/web-server 依赖。
**本原则是「守住现状」，不是「待改造」。**

## 与两条原则的关系

它们从不同方向管同一件事——**框架该长什么、不该长什么**：

- §1 管**纵向**：这个抽象该不该存在（需求真不真）。
- §2 管**横向**：这个依赖该不该跨进来（边界破没破）。

一个提案可能同时受两条约束：比如「给 core 加个 SSE 适配器」——§2 直接否（core
不碰 web 框架），§1 也会问「用户自己往 sink 写 token 要几行？」。
